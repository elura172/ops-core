ops-core · tiktok shop pipeline

Every path through this system ends at a gate that can say no

An operations core for an authorized TikTok Shop integration. Nothing mutates the shop without a human approving it, and nothing reaches live mode without a checklist attesting to it. This is where each refusal lives and what triggers it.

The shape of it

Two things arrive from outside: order events pushed by the platform, and operators making decisions. They meet two separate stores and never share a path.

Order state and review state are separate SQLite databases. A webhook can never reach the executor; an operator can never write order state.

Order events

Webhook delivery is neither ordered nor exactly-once, so an event that isn’t the next lifecycle step is normal traffic — not an error. Each event is classified against what’s already stored, inside one BEGIN IMMEDIATE transaction. 

flowchart LR
  RECEIVED --> PAID --> FULFILLMENT_PENDING --> LABEL_CREATED --> SHIPPED --> IN_TRANSIT --> DELIVERED
  SHIPPED --> DELIVERED
  RECEIVED --> CANCELLED
  PAID --> CANCELLED
  FULFILLMENT_PENDING --> CANCELLED
  LABEL_CREATED --> CANCELLED

Reachability in this graph decides every outcome below. DELIVERED and CANCELLED are terminal and unreachable from each other — which is why a cancellation arriving after delivery is a conflict rather than a transition.

What each arrival does

Arriving eventOutcomeHTTPEffect on stored state
Next step, or a jump forward applied 200 Status advances; the states never observed are logged as skipped
Status already held unchanged 200 None
event_id seen before duplicate 200 None
A step already passed stale 200 None — the order never regresses
Unreachable in either direction quarantined 202 Stored for a human; order untouched
Bad signature rejected 401 None
Missing required fields rejected 400 None
Storage failed error 500 None — the platform retries
Why the status codes matter. Anything answered 200 is recorded by TikTok as delivered and never resent. That’s why a storage failure has to be a 500, and why a conflict is captured durably before it can be answered at all.

Quarantined events surface at GET /orders/quarantined and are closed with POST /orders/quarantined/{event_id}/resolve. An order first seen mid-lifecycle has an estimated creation time, so it’s excluded from the fulfillment SLA rather than judged against a timestamp that was inferred.

Approval and execution

Anything that would change the shop becomes a review item. Approving it is necessary and never sufficient. 

stateDiagram-v2
  [*] --> PENDING
  PENDING --> REJECTED : decide(approve=false)
  PENDING --> APPROVED : decide(approve=true)
  APPROVED --> EXECUTING : claim (conditional UPDATE)
  EXECUTING --> EXECUTED : adapter returned
  EXECUTING --> FAILED : adapter raised
  EXECUTED --> EXECUTED : replay returns stored result
  FAILED --> [*] : needs a fresh approval
  REJECTED --> [*]
  EXECUTED --> [*]

The claim is an UPDATE … WHERE status = 'APPROVED' inside a transaction, so a replay, a restart, or a second worker racing the same approval cannot run the mutation twice. Failure is terminal on purpose: the outcome of a partial mutation is unknown, so a human re-approves rather than a retry duplicating it.

Identity comes from the bearer token, never the request body. Only SHA-256 digests are configured, so the environment file never holds a usable credential. With OPS_TOKENS empty every review endpoint answers 503 — an unconfigured deployment is a fault, not open access.

From agent to shop

Agents draft; they never act. Each one produces a review item, and every operation they can produce has a handler waiting — so an approval never dead-ends. 

flowchart LR
  A["prepare_publish"] --> RV["review item"]
  B["draft_customer_response"] --> RV
  RV --> H{"human decision"}
  H -->|rejected| END["stops here"]
  H -->|approved| P{"adapter enabled?"}
  P -->|"PUBLISH_ENABLED=false"| K["refused — approval kept"]
  P -->|enabled| D["DryRunPublisher / mailer"]

The executor’s allowlist is five operations: create_product_draft, update_inventory, update_prices, publish, and send_customer_response. A disabled adapter is checked before the item is claimed, because publishing being switched off is a configuration state, not a failed mutation — flip the flag and execute the same item.

Customer-response reviews hold the recipient and message body, since nobody can approve a message they can’t read. That content stays in REVIEW_DB: never logged, never returned in an execution result.

Going live

The launch gate runs at startup, before a live client can be constructed. An unattested deployment fails to boot rather than failing at its first mutation. All seven must hold.

DRY_RUN=false intent States that live mode is wanted.
LIVE_ENABLED=true intent A second deliberate act, so one stray flag isn’t enough.
secrets_configured derived Every TTS_* value present. Not self-declarable.
approval_required derived OPS_TOKENS configured — approval is only a control if the reviewer can be authenticated. Not self-declarable.
signing_verified attested A human confirms request signing was verified against Partner Center.
sandbox_passed attested A human confirms the sandbox flow was exercised.
pii_controls_verified attested A human confirms the data-handling controls.

Nothing in the process can verify that a sandbox run happened, so the three attestations record a human’s claim — and the audit trail records who deployed it. LIVE_ENABLED and the LAUNCH_* flags are inert while DRY_RUN=true.

Every way this system says no

  • no token Review endpoints answer 401; wrong role answers 403.
  • no OPS_TOKENS 503 on every review endpoint, rather than serving unauthenticated.
  • already executed Returns the stored result without re-invoking the client.
  • execution failed Terminal. Needs a fresh approval — never an automatic retry.
  • adapter off Refused before the claim, so the approval survives.
  • unattested The process refuses to start in live mode.
  • restricted claim Generated copy carrying a health or performance claim is blocked inside the provider.
  • budget spent Model calls stop once the call or token cap is reached.
  • public topic Alerts carrying order IDs won’t publish to an unauthenticated ntfy topic.
  • margin impossible Pricing raises rather than returning a number that loses money.

Where the money math lives

target_price is fee-aware. Marking cost up by the target margin alone ignores commission, transaction fees, VAT, and refunds — which is how a listing that looks 50% profitable sells at a fraction of it.

The default rates in PricingModel are placeholders. Confirm commission and VAT for your category and market before pricing anything real.

What isn’t built yet

TikTokClient is deliberately a boundary, not a fake implementation. No live call has ever been made. app/api/signing.py is an unverified canonicalization scaffold and isn’t wired into the client — which is exactly what LAUNCH_SIGNING_VERIFIED attests to, so don’t set it yet.

Unexecuted here. The container image has never been built and CI has never run — no Docker daemon was available. What is verified is the packaging they depend on and both launch-gate environment matrices, replicated locally. Whether himalaya message send accepts a stdin message is version-dependent; its test proves the body stays out of argv, not that delivery works.
Current API versions, scopes, signatures, categories, warehouse IDs, and shipping providers must come from TikTok Shop Partner Center and be exercised in its sandbox before any of this goes live.
